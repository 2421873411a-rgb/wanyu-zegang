# ADR-001：静态站与 wan-api 的产品边界

- 状态：已接受（Accepted）
- 日期：2026-09-09
- 决策者：皖域择岗窗口执行（首席工程师/QA/SRE 会签）
- 关联：ADR-002（canonical 镜像与发布）、ADR-003（用户状态同步）、CONTRACT.md §1

## 背景

项目存在两个产品形态：

1. **正式静态站 `网站/`**（wan.kaogong.art 由其构建产物部署）：三周期岗位检索、为我匹配、
   地图、待遇、审计、日历、收藏与快照，收藏/对比/快照全部落在浏览器 localStorage；
   版本真源 `项目源码/release.json`（wanyu-release/v1，现 v17.9.0）。
2. **wan-api**（FastAPI + PostgreSQL）：用户系统、岗位读取、管理导入、审计面，具备完整
   门禁测试（pytest SQLite/PG+Redis 双后端、e2e 真数据、部署链 linkage），版本真源
   `项目源码/wan-api/release.json`（wanyu-api-release/v1，与网站版本互不捆绑）。

wan-api 已具备 staging 级质量，但**从未被正式静态站消费**；静态站的云端能力（登录、云收藏、
云快照、冲突合并、降级策略）不存在任何实现。

## 决策

1. **静态站继续作为当前唯一正式产品**；wan-api 保持 staging backend 定位。
2. **不做半成品接入**：若无法完整交付 登录 → access/refresh token → 云收藏/快照/对比 →
   本地迁移 → 冲突合并 → 离线降级 → 401/403/429/503 UX 的全链路，则一行接入代码都不进
   静态站。半成品接入会让"看起来有云端同步"成为最危险的静默失败（用户以为已保存）。
3. 未来动态化必须经 **feature flag** 灰度，且默认关闭；flag 关闭时站点行为与纯静态版
   逐字节等价（含错误路径）。
4. 两版本源永远独立（网站 wanyu-release/v1；API wanyu-api-release/v1），任何"统一版本号"
   的提议都视为破坏发布语义。
5. API 文档（README）保持 "EXPERIMENTAL / NOT FOR PRODUCTION" 头直至 CONTRACT §7
   上线前置全部有真实证据（fresh-host、PG restore、COS 异机、回滚、公网 smoke）。

## 理由

- 静态站零后端依赖、零运维面、数据不可变快照——对"招考信息查询"场景是正确的产品形态。
- 用户状态云同步引入账号体系后，故障面（认证/限流/隐私/删除权）呈台阶式上升；在真实
  生产证据闭环之前接入，等于把 staging 的不确定性注入正式产品。
- localStorage 模式的失败模式（本地损坏、换机丢失）是**显式**的；半成品云同步的失败模式
  （静默丢数据）是**隐式**的。产品宁可显式也不隐式。

## 后果

- 正面：发布节奏解耦（站点与 API 独立演进）；staging 可以激进实验而不伤产品。
- 负面：用户换机/清缓存丢收藏——由站内显式文案与 CSV 导出对冲（ADR-003 承接）。
- 中性：wan-api 的生产资格证据（CONTRACT §7）按自身节奏补齐，不阻塞站点。

## 合规检查

- 本 ADR 不改变任何数据流：canonical → 静态产物 → API mirror 单向（ADR-002）。
- 2026-09-09 窗口内所有改动（v17.9.20/v17.9.21）均为测试/部署链修复，未引入任何接入代码。
